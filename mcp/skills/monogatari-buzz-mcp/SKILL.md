# 物語バズメーカー のMCP操作

## 利用の提案

ユーザーの目的にこのアプリが合い、今回のスキル利用が未指定なら、「物語バズメーカーの制作スキルを使って進めますか？」と一度提案し、選択を尊重する。同じ依頼で利用が承諾済みなら接続確認へ進む。ユーザーが選んだ別のアプリを置き換えない。

## 操作手順

1. `buzz_capabilities` で対象アプリ、接続、稼働中ジョブ、API準備状況を確認する。未接続なら `buzz_connection` の一時URLを実行チャットの内蔵ブラウザーで開く。自分で接続できなければ対象画面を示してユーザーに接続を依頼する。APIキーはアプリの通常の入力欄にだけ入力し、チャットやMCP入力には含めない。
2. `buzz_generate_brief` の `input.category` に `story-manga`、`short-video` など対象カテゴリのIDを渡す。既存の設定とプロバイダーを使う。通常画面でAPI接続と「情報収集・分析・企画作成を開始」を確認し、進行中の先行処理が終わってからジョブを投入する。取得や分析に失敗した場合は取得根拠を作らず、返されたエラーを確認する。
3. 生成ごとに固有の `requestId` を使い、同じ操作の再送には同じIDを使う。返ったジョブIDを `buzz_job_get` で追い、採用候補は実際の成果物で確認する。中止指示は `buzz_job_cancel` に渡して結果まで確認する。`unknown` では再生成せず、同じアプリの出力履歴を確認する。
4. `reportMarkdown` の根拠リンク、取得情報と企画を確認する。ユーザーが選んだ企画の `planPrompts` を `story_generate_manga_script` の `input.brief` に渡せる。公開情報を元にした事実と創作上の提案を区別し、既存のX利用設定を変更しない。

## 企画の根拠を確認する

- 期間や地域の指定があれば、採用する主要情報の配信日・出来事の日付・出典リンクを抽出し、元記事で照合する。転載や同一発表を複数回数えない。公開日時や本文を確認できない項目は未確認とし、断定の材料から外す。
- 元記事で確認できた事実、分析からの推定、創作で足す設定が分かる形で候補を出す。閲覧数や反応が取得できなければ人気順や実測値を付けない。取得障害で根拠が足りなければ、取得できた範囲と不足を示す。
- 採用案をStory Makerに渡すときは、元記事のURL、事実として守る点、創作してよい点を概要に添える。同じ記事でも採用案が変わったら、前の企画や人物設定が混ざっていないか照合する。
